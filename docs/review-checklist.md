# 서비스 점검 체크리스트

`.github/workflows/quality-review.yml`이 매일 이 목록으로 서비스를 점검한다 (`scripts/quality_review.py`).
Claude(기본 `claude-haiku-5-5`)가 코드·운영 사이트 응답·최근 24시간 운영 요약을 읽고 항목마다 ok / fix / manual로 판정한다.
- **fix**(코드로 고칠 수 있음) → `[품질]` 이슈 → 자동 수정(`autofix.yml`, Claude Fable) → 수정 PR → 주인 승인 → 배포
- **manual**(사람이 해야 함: Vercel 설정·플랜, 비밀 값, 보호 파일 등) → 보고서에만 적는다
- 서버 부하 때문에 Vercel 플랜을 올려야 하면 `[용량]` 이슈를 연다 (결제는 사람이 한다)

## 서비스 이해
- 우리 서비스는 어떤 문제를 해결하는 서비스인가?
- 사용자는 우리 서비스를 통해 어떤 가치를 얻는가?

## 기술 스택
- 현재 기술 스택을 선택한 합리적인 근거가 있는가?
  - 다른 대안과 비교했을 때 현재 기술을 선택한 이유는 무엇인가?

## 확장성
- 현재 코드 및 시스템 구조는 사용자 증가를 감당할 수 있는가?
  - 감당하기 어려워지는 지점은 어디인가?
  - 한계에 도달했을 때 어떤 구조로 확장하거나 변경할 수 있는가?
- 캐시정책이 적절하게 설정되어 있는가?
- 배포시 사용자가 예전 캐시된 페이지를 보고 있다면 어떻게 무효화 할 수 있을까?

## 외부 서비스 의존성
- 외부 서비스(AI API 등)에 장애가 발생하면 우리 서비스는 어떻게 동작하는가?
  - `429 Too Many Requests`가 발생하면 어떻게 처리하는가?
  - 외부 서비스가 응답하지 않으면 얼마나 기다린 후 요청을 중단하는가?
  - Timeout, Retry, Fallback 정책은 어떻게 구성되어 있는가?
  - 다른 외부서비스로 쉽게 교체가 가능한 구조인가?

## 장애 대응 및 로깅
- 서비스 장애가 발생했을 때 로그를 기반으로 원인을 파악하고 복구할 수 있는가?
- 로그는 어디에, 어떤 형식으로 저장하는가?
- 어떤 수준의 로그를 남겨야 하는가?
- DB 또는 백엔드 서버에 장애가 발생하면 서비스는 어떻게 동작하는가?
  - DB 또는 서버에 장애가 발생할 수 있는 주요 원인은 무엇인가?
  - 장애 발생 후 어떻게 감지하고 복구하는가?

## 인증 및 보안
- 인증(Authentication)과 인가(Authorization)는 어떻게 처리하는가?
- 동일한 사용자가 여러 기기에서 동시에 접속하면 어떻게 처리하는가?
- 악의적인 사용자 입력은 어떻게 검증하고 차단하는가?
- 쿠키가 위변조되면 어떻게 탐지하고 대응하는가?

## 사용자 경험 및 예외 처리
- 응답 시간이 길어질 경우 사용자에게 진행 상태를 어떻게 안내하는가?
- 오류가 발생했을 때 사용자에게 어떤 정보를 제공하는가?
- 클라이언트의 네트워크가 느리거나 연결이 끊어지면 어떻게 처리하는가?
- 요청 실패 후 사용자가 안전하게 다시 시도할 수 있는가?
- UI/UX를 고려했는가?
  - 서비스 목적에 맞는 UI/UX인가?
  - UI와 UX의 차이는?

## 비동기 처리
- `await` 키워드는 무엇을 의미하는가?
  - 비동기 처리는 어떤 원리로 동작하는가?
  - 이벤트 루프(Event Loop)는 무엇인가?

## 웹 표준 및 접근성
- 웹 표준과 접근성 기준을 준수하고 있는가?
  - 키보드의 `Tab` 키만으로 모든 주요 기능과 버튼에 접근할 수 있는가?
- 오픈그래프, 파비콘이 설정되어 있는가?

## 코드 품질 및 유지보수성
- 현재 코드 구조를 다른 개발자가 쉽게 이해할 수 있는가?
- 새로운 작업자가 코드베이스를 빠르게 파악하고 수정할 수 있는가?
- 각 모듈의 책임과 의존관계가 명확하게 분리되어 있는가?
- 불필요한 API요청이 있는가?

## LLM
- LLM 답변 품질을 개선하기 위해 어떤 노력을 했는가?
- 답변품질을 정량적으로 혹은 정성적으로 측정하기 위해 어떤 방법을 사용했는가?
